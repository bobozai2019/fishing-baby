# 当前技术架构

## 1. 文档目的

本文描述 `fishing-baby` 当前已经落地的技术架构，包括运行时模块、代码组织、场景与资源关系、状态机、信号流、输入和渲染方式、测试与导出工具，以及目前存在的架构约束。

本文是现状说明，不把尚未实现的多关卡、存档、联网或通用框架能力视为已有功能。

## 2. 架构定位

项目基于 Godot 4.7 和 GDScript，采用以场景树为主体的模块化单体架构：

- Godot 场景负责静态对象树、节点组合、初始布局和资源装配。
- GDScript 负责状态机、运行时规则、事件编排和视觉状态更新。
- 自定义 `Resource` 负责关卡参数和可捕获物配置。
- Signal 负责游戏模块之间的事件通知。
- `Main` 是当前唯一的应用级组合根，负责连接各模块并编排一局游戏。

它不是 ECS、MVC、依赖注入框架或全局事件总线，也不是面向多个游戏复用的通用玩法框架。当前结构针对单场景核心玩法 Demo，优先保持节点关系直观、代码量小和运行路径明确。

## 4. 总体分层

```text
输入事件
   │
   ▼
Main（组合根 / 应用编排）
   ├── GameSession（模式、角色选择与活动玩家）
   ├── RoundController（回合状态与计分）
   ├── WaveController（三波激活与重置）
   ├── HookController ×2（抓钩运动、捕获与道具触碰）
   ├── Catchable / PowerupPickup（计分目标与即时道具）
   ├── PowerupEffectController（临时效果计时与恢复）
   └── UI（模式/角色选择、HUD、结算层、即时反馈）
          │
          ▼
CharacterDefinition / LevelDefinition / CatchableDefinition（Resource 配置）
```

### 4.1 应用编排层

`scripts/main.gd` 是当前应用的组合根，主要职责如下：

- 获取主场景中的控制器、实体容器和 UI 节点。
- 编排“模式选择—单人角色选择—准备—游戏—结算”应用流程。
- 根据 `GameSession.active_player_ids` 配置船、抓钩、计分、个人道具和 HUD。
- 在 `_ready()` 中连接模块信号。
- 按回合状态分发开始、重新开始和发射输入。
- 将鱼叉交付结果转换为得分。
- 在回合结束时禁用鱼叉并展示结算层。
- 重置回合、三波实体、临时效果、双钩和 UI。
- 根据视口尺寸水平居中 1920 像素宽的玩法构图，并在竖屏中扩展水下区域与下移沙床。

`Main` 不实现鱼叉运动或回合计时等领域规则，而是把各模块组合成完整流程。

### 4.2 玩法领域层

玩法领域由回合、双钩、可捕获物、道具和波次控制组成：

- `RoundController`：控制准备、进行中、胜利和失败。
- `HookController`：控制摆动、伸出、空钩收回和带物收回。
- `Catchable`：控制可捕获、已挂钩和已收集。
- `PowerupPickup`：控制可用与已消费。
- `WaveController`：保证 0/30/60 秒激活幂等并在重开时恢复 Wave 1。
- `PowerupEffectController`：按效果种类和玩家计时，处理刷新、共存和清除。

状态机将允许的操作限制在明确状态内，避免输入、碰撞和结算事件重复生效。

### 4.3 数据定义层

数据定义使用 Godot `Resource`：

- `CharacterDefinition` 保存稳定 ID、显示名、选择头像、船上头部贴图和排序值。
- `LevelDefinition` 保存时长、目标分数、摆角、速度和绳长等回合及鱼叉参数。
- `CatchableDefinition` 保存标识、显示名、分类、分值、重量、移动类型、速度、贴图缩放和碰撞尺寸等实体参数。
- `PowerupDefinition` 保存效果类型、5 秒时长、倍率、贴图与碰撞尺寸。
- `LevelDefinition` 额外保存三波已用时间阈值。

具体配置位于 `resources/game_data/`。这种结构使数值和关卡装配可以通过编辑器调整，而不必修改玩法代码。

### 4.4 表现层

表现层由场景和 UI 脚本组成：

- `FishingLevel` 承载海洋环境、船、鱼叉、可捕获物和局内反馈。
- `GameSetupOverlay` 展示模式选择，并从角色 Resource 目录动态生成单人角色卡。
- `GameHud` 展示时间、分数、目标和准备提示。
- `RoundResultOverlay` 展示胜负结果并发出重新开始请求。
- `CanvasLayer` 将 HUD 与被缩放的玩法区域分离。

UI 脚本以展示和转发用户意图为主，不负责计分、计时或捕获判定。

### 4.5 工具与验证层

- `tests/run_core_tests.gd`：核心逻辑和场景契约的自动化测试入口。
- `tests/e2e/*.spec.ts`：真实浏览器 canvas 输入、玩法流程、视口与 Web 回归。
- `tests/visual_playing.tscn`：用于运行态视觉检查的测试场景。
- `scripts/tools/capture_scene.gd`：无窗口场景加载和截图辅助脚本。
- `tools/serve_web.py`：为 Web 构建提供带跨源隔离响应头的本地静态服务器。

`scenes/entities/boat.tscn` 替代了原先直接放置整张船图的方式。场景由以下节点组成：

- `RopeOrigin`：保存该船对应的绳索参考点，继续维持既有节点契约。

`scenes/environment/ocean_environment.tscn` 实例化两次 `boat.tscn`：`Boat` 保留默认男孩头，`Boat2` 将 `Head.texture` 覆盖为 `resources/characters/girl_head.png`。船身与角色头部的缩放、相对位置均保存在 `boat.tscn`，环境场景只负责实例位置和实例差异。

## 7. 核心运行流程

### 7.1 配置游戏会话

```text
启动 → GameSession.MODE_SELECT
  ├─ 单人 → CHARACTER_SELECT → 选择 CharacterDefinition → active_player_ids=[1]
  └─ 多人 → 使用默认男孩/女孩 → active_player_ids=[1,2]
       ↓
Main 装配角色头部、船/钩可见性、HUD 与有效输入
       ↓
GameSession.READY + RoundController.READY
```

角色身份和逻辑玩家槽位分离：单人无论选择哪名角色都使用 P1 计分与抓钩链路，P2 完整禁用；本地多人继续使用 P1/P2。

### 7.2 开始回合

```text
开始输入 / HUD 请求
  → Main 检查回合状态
  → RoundController.start_round()
  → 状态切换为 PLAYING
  → HookController 启用并进入 SWINGING
  → HUD 隐藏准备提示并开始更新时间
```

### 7.3 发射与捕获

```text
发射输入
  → Main 检查当前是否为 PLAYING
  → HookController.try_launch()
  → EXTENDING
  → Tip 与 Catchable 的 Area2D 相交
  → Catchable.attach_to_hook(CollisionShape2D)
  → 目标当帧吸附到钩爪碰撞中心并进入 HOOKED
  → HookController 进入 RETRACTING_CATCH
  → 收回到绳索原点
  → 再次确认目标仍处于 HOOKED
  → Catchable.collect()
  → delivery_completed
  → Main 调用 RoundController.add_score()
```

鱼叉一次只携带一个可捕获物。捕获时以钩爪的 `CollisionShape2D` 作为载体，目标立即移动到碰撞中心，并临时使用位于场景装饰之上、钩爪之下的显示层级。空钩到达最大长度后进入 `RETRACTING_EMPTY`，回到原点后重新摆动，不发出 `delivery_completed`，且 `shot_completed.caught_something` 为 `false`。

交付分支不能只依赖缓存的对象引用：`HookController` 在发出 `delivery_completed` 前必须同时确认对象有效且仍处于 `CatchableState.HOOKED`。校验失败时按空钩完成，不产生分数。该约束与 `RoundController` 的实例 ID 去重共同构成“有效挂钩 + 单次交付”计分边界。

### 7.4 结算与重开

```text
达到目标分数或时间归零
  → RoundController 发出 round_finished
  → Main 禁用 HookController
  → HUD / RoundResultOverlay 显示结果

重新开始请求
  → Main 重置三波与全部实体
  → 清除临时效果并重置两个 HookController
  → 隐藏结算层
  → RoundController 回到 READY
```

## 8. 状态机定义

### 8.1 应用会话状态

| 状态 | 含义 |
|---|---|
| `MODE_SELECT` | 等待单人/多人选择 |
| `CHARACTER_SELECT` | 单人等待角色选择 |
| `READY` | 会话已配置，等待开始回合 |
| `PLAYING` | 当前回合进行中 |
| `RESULT` | 当前回合已结算 |

“再来一局”从 RESULT 返回 READY 并保留模式与角色；“返回模式选择”清空会话，并在复位波次、效果和抓钩后返回 MODE_SELECT。应用状态不并入 `RoundController`，后者继续只负责单局规则。

### 8.2 回合状态

| 状态 | 含义 | 主要允许行为 |
| --- | --- | --- |
| `BOOT` | 节点尚未完成初始化 | 无 |
| `READY` | 等待玩家开始 | 开始回合 |
| `PLAYING` | 计时和计分中 | 发射、捕获、加分 |
| `WON` | 已达到目标分数 | 重新开始 |
| `LOST` | 时间结束且未达目标 | 重新开始 |

`RoundController` 使用可捕获物实例 ID 去重，保证同一实体不会被重复计分。

### 8.3 鱼叉状态

| 状态 | 含义 |
| --- | --- |
| `DISABLED` | 回合未开始或已经结束 |
| `SWINGING` | 在绳索原点摆动并等待发射 |
| `EXTENDING` | 沿当前方向伸长 |
| `RETRACTING_EMPTY` | 未捕获物体时收回 |
| `RETRACTING_CATCH` | 携带捕获物收回 |

携带物重量会影响收回速度。鱼叉视觉、碰撞形状和绳端都由同一方向向量及绳长计算，以维持运行时对齐。

### 8.4 可捕获物状态

| 状态 | 含义 |
| --- | --- |
| `AVAILABLE` | 可运动、可碰撞、可被捕获 |
| `HOOKED` | 当帧吸附到钩爪碰撞中心、关闭碰撞并持续跟随鱼叉 |
| `COLLECTED` | 已交付、隐藏且不可再次捕获 |

重开回合时，每个实体恢复到初始位置、可见性、碰撞和运动状态。

## 9. 通信与依赖规则

当前依赖方向如下：

- `Main` 依赖回合、鱼叉、实体和 UI 模块，并负责跨模块编排。
- `GameSession` 依赖显式角色 Resource 目录，提供模式、角色槽位和活动玩家集合。
- `RoundController` 依赖 `LevelDefinition`。
- `HookController` 依赖 `LevelDefinition`、`Catchable` 与 `PowerupPickup` 的公开行为。
- `Catchable` 依赖 `CatchableDefinition`。
- `PowerupPickup` 依赖 `PowerupDefinition`；效果控制器通过公开倍率接口和 `aquatic_life` group 施加/清除效果。
- UI 接收展示数据并发送开始或重开请求。
- 领域模块通过 Signal 向上报告事件，组合根再调用其他模块完成下一步。

主要 Signal 包括：

- 回合：状态变化、分数变化、时间变化、回合结束。
- 鱼叉：状态变化、捕获附着、交付完成、单次发射完成。
- 可捕获物：已挂钩、已收集。
- UI：开始请求、重新开始请求。
- 会话 UI：单人、多人、角色确认、返回模式选择请求。

项目当前没有全局单例、服务容器或消息总线。跨模块行为应优先通过组合根编排，避免玩法节点互相查找并修改内部状态。

## 10. 输入、坐标与渲染

### 10.1 输入映射

- `cast_hook`：空格或鼠标左键。
- `start_round`：空格或 Enter。
- `restart_round`：空格或 Enter。

相同按键在不同回合状态下具有不同含义，`Main._unhandled_input()` 根据当前状态进行路由并消费事件。

模式和角色选择期间，覆盖层阻挡下层玩法输入。单人游戏中 Q、空格和任意合法水域点击/触控都路由至 P1；P、右键及右半区不再产生 P2 操作。多人继续使用 Q/P 与左右水域分区。

### 10.2 坐标与缩放

玩法区以 1920 像素宽为设计坐标。横屏保持 1920 × 1080 基准构图；竖屏增加水下区域高度，九宫格海洋背景随可见区域拉伸，三宫格沙床锚定视口底部。`Main` 将玩法内容水平居中；HUD 位于独立 `CanvasLayer`，竖屏使用 1080 像素虚拟宽度单独放大，避免手机触控区过小。鱼钩按当前摆角计算与沙床顶线的交点，并预留碰撞半径，避免钩体越过实际河床。

### 10.3 鱼叉与绳索

绳索使用 `Line2D`，鱼叉尖端使用 `Area2D`。鱼叉方向由摆角计算，绳长决定末端位置。精灵中心和碰撞中心存在资源相关的固定偏移常量，因此替换鱼叉图片、调整图片缩放或碰撞尺寸时，必须一并复核绳端、精灵热点和碰撞中心的对齐。

## 11. 数据与内容扩展方式

### 11.1 增加同类可捕获物

如果新物体能够复用现有运动和捕获规则，只需：

1. 新建一个 `CatchableDefinition` `.tres`。
2. 在关卡场景中添加 `Catchable` 场景实例。
3. 分配唯一的定义 ID 和实例 ID。
4. 配置位置、移动边界和对应资源。

不需要为每个鱼类或垃圾物体新建脚本。

### 11.2 增加新的运动规则

当前运动模式由 `CatchableDefinition.MovementType` 和 `Catchable` 中的分支实现。增加一种新运动方式需要同步修改枚举、实体运动逻辑和测试。

### 11.3 增加新关卡

数据层已能通过新的 `LevelDefinition` 表达不同回合参数，但当前 `Main` 的节点路径和 Demo 场景装配是固定的。单纯复制配置不能构成完整的多关卡系统；若要支持关卡选择、切换和进度，需要增加明确的关卡会话或场景切换层。

### 11.4 增加可选择角色

1. 新建合法的 `CharacterDefinition` `.tres`，提供唯一 ID、名称、头像和船上头部贴图。
2. 将资源加入 `GameSession.characters` 显式目录。
3. 选择界面会按 `sort_order` 和 ID 稳定排序并自动生成角色卡，不需要增加角色名分支。

当前角色只改变视觉身份；专属技能、属性、解锁和多人角色自选不是已实现能力。

## 12. 测试架构

`tests/run_core_tests.gd` 是轻量级自定义测试运行器，当前覆盖：

- 主场景必要节点、三波 19 个实体、16 个计分实例、3 个道具和 3920 总分的场景契约。
- 两个 Boat 实例的 `Body`、`Head`、`RopeOrigin` 节点，以及船身、男孩头和女孩头的资源绑定。
- 角色 Resource 校验、三角色目录排序、选择卡自动生成和会话非法迁移拒绝。
- 单人女孩装配、P2 船/钩隐藏、P2 计分与个人效果拒绝、单人超时失败、重开保留和返回菜单复原。
- 定义 ID、实例 ID 唯一性、4 种新移动、波次阈值和 Powerup Resource 参数合法性。
- 回合开始、重复开始拒绝、计分去重、胜利、失败和重置。
- 连续 20 次空钩发射与收回，并断言 0 次交付、0 次命中完成报告。
- `Area2D` 实际碰撞、当帧可见挂钩和单次交付链路。
- 可捕获物重复附着拒绝、收集和重置，以及道具即时消费、个人效果隔离、同类刷新、效果共存和全局冰冻。

测试直接驱动部分 `_physics_process()`，并通过 `force_time_expired_for_test()` 触发超时，因此测试速度快、结果稳定，但不能替代真实帧率下的手感、UI 点击区域和视觉对齐检查。视觉问题应配合 headless 场景加载、截图和人工检查验证。

Playwright E2E 使用独立 `Web E2E` preset、Chromium/Edge 和单 worker 运行。它通过真实 canvas 点击/键盘驱动主要流程；仅在构建具有 `e2e` feature 且 URL 带 `?e2e=1` 时，`scripts/tools/e2e_bridge.gd` 才发布 canvas 内状态和确定性测试命令。普通 `Web` preset 不启用该接口。运行方式、用例矩阵和当前失败见 `tests/e2e/README.md` 与 `docs/testing/`。

## 13. 导出与运行辅助

当前 `export_presets.cfg` 只包含 Web 导出预设。Web 本地运行使用 `tools/serve_web.py` 添加 COOP、COEP 和 CORP 响应头，以满足跨源隔离要求。

如果需要恢复 Windows 导出，应重新建立并验证 Windows Desktop 预设；不能根据旧任务记录假定该预设仍然存在。

编辑器中启用了 GodotIQ 和 Editor Logger 插件，它们属于开发辅助能力，不应成为游戏运行时逻辑的依赖。

## 14. 当前约束与技术债

以下内容是现有实现的边界，不代表必须立即重构：

- `Main` 同时承担输入路由、信号装配、流程编排、反馈文字和玩法区缩放；对当前 Demo 合理，但继续增加关卡、教程或暂停系统时会变得过于集中。
- `GameSession` 的角色目录当前直接装配在 `main.tscn`；角色数量显著增加时可能需要独立目录 Resource，但当前两角色不需要再抽象一层。
- 静态信号关系在代码中连接，而非保存在 `.tscn`；阅读运行流方便，但与“静态关系尽量场景化”的项目约定存在轻微偏差。
- `GameHud` 和结算 UI 使用 `RoundController` 的枚举，表现层对领域类型存在直接依赖。
- 重置逻辑遍历 `DemoCatchables` 的直接子节点并进行类型判断，依赖当前固定场景结构。
- `RoundController.add_score()` 接受调用方传入的分数，只负责实例去重；当前可信调用链来自鱼叉交付，但控制器自身不会核对分数是否等于定义值。
- 鱼叉精灵和碰撞对齐依赖硬编码热点偏移，资源发生变化时需要回归检查。
- `force_time_expired_for_test()` 是为测试暴露在运行时代码中的辅助入口。
- 捕获物通过具体的鱼叉载体位置跟随，没有抽象的通用携带接口。
- 当前只有 Web 导出预设；若目标仍包含 Windows，需要补回导出配置并加入验证流程。

这些约束应在实际需求出现时再做最小重构，不应提前引入通用框架、事件总线或复杂依赖注入。

## 15. 架构守则

后续实现应保持以下原则：

1. 可静态确定的节点、布局和 Resource 绑定优先保存在场景或资源文件中。
2. 状态转换只由对应控制器或实体自身执行，外部通过公开方法表达意图。
3. 模块向上报告事件使用 Signal，跨模块串联由组合根负责。
4. 数值和内容差异优先通过 Resource 配置，不复制玩法脚本。
5. 新抽象必须服务于已经出现的复用或复杂度，避免为假设需求扩展框架。
6. 每次修改鱼叉图片、碰撞形状、缩放或热点后，都要验证绳端、鱼叉和碰撞区域三者对齐。
7. 场景契约、状态机不变量和端到端捕获流程应继续由自动化测试保护。
